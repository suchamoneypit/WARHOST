# Architecture

This repository is WARHOST: an Unraid template and a settings wrapper around Eugen Systems' official WARNO dedicated-server image. The game server itself stays in `eugensystems/warno`.

Checked against the files in this repo on 2026-10-09, the Docker Hub page [eugensystems/warno](https://hub.docker.com/r/eugensystems/warno), and anonymous registry reads of `eugensystems/warno:latest` and `ghcr.io/suchamoneypit/warhost:latest`. Digests below are from that day and will change when the images are rebuilt. The rebuild workflow publishes `ghcr.io/suchamoneypit/warhost:latest` only.

## Template behavior

Unraid installs `ghcr.io/suchamoneypit/warhost:latest` from `templates/warhost.xml`. The template is `<Container version="2">`. `<Name>` is `WARHOST`. `<ExtraSearchTerms>` is `WARNO WARNO server dedicated server game server mods modded`. Paths and variables are `<Config>` entries. The default host folder is `/mnt/user/appdata/warno/10400/settings`. There is no WebUI.

On start, `WRITE_CONFIG` defaults to true. The wrapper then rewrites these files under the settings directory:

- `login.ini` from `EUGEN_LOGIN` and `EUGEN_DEDICATED_KEY`. The startup line names the last 4 characters of the key. Those characters are not a separate setting.
- `variables.ini` from the form plus the match defaults hardcoded in `entrypoint-unraid.sh`
- `params_for_ai.json` as two empty deck lists, `0` and `1`
- `warhost-workshop-versions.txt`, only when Workshop Mod List holds a bare id (see Workshop Version at start)

Those files are written mode `600`. The wrapper creates a private mode-`700` directory named `.warhost-stage.*` in the settings folder, writes the three files there, and renames them into place. A symlink at a final name is removed instead of followed. A directory at a final name stops the start. It removes that directory on exit and on `HUP`, `INT`, and `TERM`. After `warhost.lock` is held, it removes leftover real directories with that prefix and leaves symlinks with that prefix in place. A crash, `SIGKILL`, or power loss can leave one until the next locked start. `WARHOST_STAGING_HOLD` is a test seam, not a form field: when it names an existing file, the wrapper waits before that rename. `WRITE_CONFIG=false` leaves existing copies in place, sets `login.ini` to mode `600`, and exits if any of the three is missing. The wrapper does not mention `admins.ini` or `banned_clients.ini`. The README says the official server creates those two and that this wrapper leaves them alone. That server behavior was not observed here.

The form exposes login, key, public IP, port, server name, map, player counts, team size, combat rule, mod list, the write-config switch, and mod tags. The login and the dedicated key use `Mask="false"`. Map, Max Players, Minimum Players, Team Size, and Combat Rule use `Display="always"`. Map follows Server Name. Workshop Mod List, Write Config From Form, and Workshop Mod Tags use `Display="advanced"`, in that order. Field descriptions are one or two sentences. Base-game scenario IDs and the named workshop mods are in `README.md`, not in the form. Unraid's [CreateDocker.php](https://github.com/unraid/webgui/blob/master/emhttp/plugins/dynamix.docker.manager/include/CreateDocker.php) `templateDisplayConfig`, read on 2026-10-09, prints each field description under the input, and appends `Display="advanced"` fields to the Show more settings block. The wrapper also writes fixed match values: `GameType = 0`, `MapRotationType = 0`, `InitMoney = 750`, `TimeLimit = 1200`, `ScoreLimit = 2000`, `WarmupCountdown = 60`, `LoadingTimeMax = 120`, `DeploiementTimeMax = 120`, `DebriefingTimeMax = 60`, `DeltaMaxTeamSize = 0`, `IncomeRate = 3`, `Upkeep = 0`, `AllowObservers = 1`, and `ObserverDelay = 120`.

The preset in the template and sample is a 2v2 Conquest server (`NB_MAX_PLAYER=4`, `MAX_TEAM_SIZE=2`, `COMBAT_RULE=2`) on the base-game map `_2x2_Hesse_2vs2_CONQ`, with Server Name `WARHOST - Hesse 2v2`. `MOD_LIST` and `MOD_TAG_LIST` are empty in both the `Default` attribute and the element text, so the sample has no `ModList` or `ModTagList` line. Unraid's [Helpers.php](https://github.com/unraid/webgui/blob/master/emhttp/plugins/dynamix.docker.manager/include/Helpers.php), read on 2026-10-10, fills a blank `<Config>` value from its `Default` in `xmlToVar` (the edit form) and in `xmlToCommand` (the `docker run` variables), so a field with a non-empty `Default` cannot be cleared from the form. A container added from an earlier template keeps that template's `Default` in its saved `my-<Name>.xml`. The wrapper treats an unset variable and `none`, in any case, as empty for both fields. The Map and Workshop Mod List descriptions give the Red Dragon example: Map `RDPort_JungleLaw_2v2_CONQ` with `3811913066`, and tags `Maps-Scenarios`. A bare id is resolved to `id/version` before the files are written (see Workshop Version at start). `Jungle Law` and `YOUR_*` placeholders are rejected. When `ModList` is set, the wrapper prints that clients compare each `id/version` with `Version` in that mod's `Config.ini`, and that the client message does not appear in this log. When the list contains `3811913066` and Map does not start with `RDPort_`, it prints one warning that players without that mod cannot join, skips the version warning, and still writes the list. On a Red Dragon map, the typed pairs `3811913066/0` and `3811913066/15` print a warning and are still written through. A `Version` read from Steam never prints that warning. When Workshop Mod List is empty and Map is not one of the 102 base-game scenario IDs copied into the wrapper from the README table, it prints one warning and still starts. When Workshop Mod Tags is set and Workshop Mod List is empty, it prints a note that the tags are written and do not select a mod. Public WAN IP stays empty. Unraid's [CreateDocker.php](https://github.com/unraid/webgui/blob/master/emhttp/plugins/dynamix.docker.manager/include/CreateDocker.php), read on 2026-10-09, fills the Add Container form from the template XML and only rewrites the `/config` and `/unraid` path defaults. The install guide points at <https://www.whatismyip.com/>.

## Paths

| Location | Path |
| --- | --- |
| Container settings | `/server/settings` |
| Default Unraid host path | `/mnt/user/appdata/warno/10400/settings` |
| Wrapper entrypoint | `/server/entrypoint-unraid.sh` |
| Upstream entrypoint | `/server/entrypoint2.sh` (`UPSTREAM_ENTRYPOINT` can override it) |

A second server is another container from the same template, with its own name, Game Port (the previous port plus 1), Server Name, and settings folder. The first host folder is `/mnt/user/appdata/warno/10400/settings`. An added server uses that same path with its own Game Port, for example `/mnt/user/appdata/warno/10401/settings`. Those folders hold the ini files. The wrapper takes an exclusive `flock` on `warhost.lock` in that directory and holds the fd across `exec` until the server process exits. If `flock` is missing, it warns and continues. Eugen's Docker Hub page says one login and key pair can start a maximum of five servers: [Obtaining access key](https://hub.docker.com/r/eugensystems/warno). Fifteen servers need three pairs, fifty need ten, and one hundred needs twenty. The published image is one shared copy. There is no game-library volume.

## Networking

The template sets `<Network>host</Network>` and defines no port mapping. `EXPOSEDIP` and `EXPOSEDPORT` are environment variables read on each start. The default port in the template is `10400`. Eugen's start example uses a placeholder port, so `10400` is a choice of this repository. Editing the container and applying a new `EXPOSEDPORT` changes the listen port; the router forward has to use the same number. The next container's Game Port is that number plus 1. One server uses that one port: forward it as TCP and UDP, not as the port and the port plus 1. Players join by Server Name. Eugen's page does not say the port is fixed after the first start.

Before exec, the wrapper reads `tcp`, `tcp6`, `udp`, and `udp6` under `WARHOST_PORT_TABLE` (default `/proc/net`, which host networking shares with the host). It stops if this Game Port is a local TCP socket in state `0A` (LISTEN) or a local UDP socket in any state. TIME_WAIT and the other TCP states do not count, so a port left behind after a stop does not force a new folder or Server Name. The first line of each file is skipped as a header. Only the local-address column is compared. `WARHOST_PORT_TABLE` is not a template field. Two containers started in the same moment can both pass this check.

Eugen recommends host networking and says to forward both TCP and UDP to the exposed port: [Starting docker container](https://hub.docker.com/r/eugensystems/warno). The image config read on 2026-10-09 has no `ExposedPorts`.

The README says outbound internet is required to reach Eugen except for LAN use. Docker Hub does not state that LAN exception. Treat it as a statement in this repository.

RCON is unset. Eugen documents `-rcon_password` and `-rcon_port` as arguments to the official container. The template leaves `PostArgs` empty. The wrapper forwards any arguments it receives to the upstream entrypoint.

## Workshop Version at start

A Workshop Mod List entry without `/` is a bare id. After the port and lock checks and before any settings file is written, the wrapper resolves each bare id, one at a time in list order, and writes `id/Version`. A typed `id/version` is a pin: it is written as typed and does not contact Steam. `WRITE_CONFIG=false` resolves nothing. The check runs once per start. There is no loop and no restart during a match.

`warhost-workshop-versions.txt` in the settings folder holds one line per bare id from the last start: `id time_updated Version`. It is staged and renamed like the other files, and it is not followed when it is a symlink. A directory at that name is left in place with a warning, and the start continues without saving. Steam's `GetPublishedFileDetails` (`POST https://api.steampowered.com/ISteamRemoteStorage/GetPublishedFileDetails/v1/` with `itemcount=1&publishedfileids%5B0%5D=<id>`, no key) returns one line of JSON with `time_updated`, `file_size`, and `hcontent_file`, and no `Version`. When `time_updated` equals the saved time, the saved `Version` is written and nothing is downloaded. When Steam gives no time and a line exists, the saved `Version` is written with a warning.

Otherwise the wrapper runs `timeout 300 DepotDownloader -app 1611600 -pubfile <id> -filelist <list> -dir <dir>/item` with no Steam account. The list holds only `Config.ini`. `<dir>` is a new mode-`700` `.warhost-stage.*` directory in the settings folder and is also `HOME`, `TMPDIR`, and the working directory. DepotDownloader starts under `env -i` with only `PATH`, `HOME`, `TMPDIR`, and two .NET settings, so it never receives the Eugen login or key. The wrapper reads the first `Version = <digits>` line and removes `<dir>` before the next id, also after a failure and on `HUP`, `INT`, and `TERM`. When the fetch fails and a line exists, the saved `Version` is written with a warning and the saved time is kept, so the next start tries again. With no line, the start stops after printing the last 5 lines of DepotDownloader's output and the reason.

Measured on 2026-10-10 with DepotDownloader 3.4.0 and no Steam account:

| Item | `file_size` | `Config.ini` transferred | Manifest saved | `Version` |
| --- | --- | --- | --- | --- |
| `3811913066` Red Dragon | 9,059,324,422 bytes | 416 bytes (551 uncompressed) | 419,989 bytes | 27 |
| `3474588989` Highway to Oslo | 148,918,317 bytes | 384 bytes (485 uncompressed) | 13,745 bytes | 14 |

The manifest IDs DepotDownloader requested, `3167211120192437934` and `7803733855267144859`, equal `hcontent_file` from the details call. For published file `1`, DepotDownloader printed `Unable to locate manifest ID for published file 1` and exited `0`, so the wrapper requires `Config.ini` on disk and does not trust the exit status alone. With networking removed it printed `Could not connect to Steam after 10 tries` and exited `1` after about 55 seconds. In [ContentDownloader.cs](https://raw.githubusercontent.com/SteamRE/DepotDownloader/DepotDownloader_3.4.0/DepotDownloader/ContentDownloader.cs) at that tag, read 2026-10-10, `DownloadPubfileAsync` passes `hcontent_file` to the depot download as a manifest ID, and the manifest's files are filtered through `TestIsFileIncluded`, which applies the file list, before any chunk is queued. In [Program.cs](https://raw.githubusercontent.com/SteamRE/DepotDownloader/DepotDownloader_3.4.0/DepotDownloader/Program.cs) at that tag, `-filelist` turns the filter on with an empty list before reading the file, so a list that cannot be read downloads nothing.

The Dockerfile downloads `DepotDownloader-linux-x64.zip` from release [DepotDownloader_3.4.0](https://github.com/SteamRE/DepotDownloader/releases/tag/DepotDownloader_3.4.0) (33,442,357 bytes, SHA-256 `a999dec66b4850fc961bd50366696d23c2d0fad7b18790e6a5647b2f19097a53`), checks the hash, and unpacks it with `python3 -m zipfile` into `/opt/depotdownloader`, with its GPL-2.0 `LICENSE`. `/usr/local/bin/DepotDownloader` links to the 78,977,777-byte self-contained binary. `DepotDownloader -V` printed `DepotDownloader v3.4.0+c553ef4d60c00a4f5fd16c9fe017f569001589ff` and `Runtime: .NET 9.0.0 on Debian GNU/Linux 13 (trixie)`. Eugen's image at digest `sha256:fb498aa82d7b15e3978bac51240e1243be3e19232ba0e66a6d947ec4b4364fe5` has six layers totaling 84,020,395 bytes compressed. It has `wget`, `sha256sum`, `python3`, `timeout`, and `flock`, has no `curl`, `unzip`, or ICU library, and its `/bin/sh` is `dash`. The wrapper sets `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1` because ICU is absent. The .NET runtime creates an empty `/tmp/.dotnet/shm` in the container regardless of `TMPDIR`.

On 2026-10-10 those layers were unpacked into a directory.
